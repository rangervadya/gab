# Прогресс и остановка импорта

## Интерфейс

При загрузке показываются текущий файл, процент, переданные/общие МиБ и приблизительный остаток передачи по её фактической скорости. 100% передачи означает ожидание ответа о сохранении файла, а не окончание OCR.

После загрузки карточка автоматически обновляется каждые три секунды. Отображаются очередь, OCR/извлечение текста, извлечение инвесторов Ollama, готовность к проверке, ошибка или остановка; число завершённых страниц текущего этапа и время с начала обработки. Оценка остатка появляется только после двух завершённых страниц и относится к текущему этапу, не к целому документу. Для одностраничного документа, очереди и старого обработчика без измерений время может оставаться неизвестным. Excel-ветка без постраничного OCR показывает этап и elapsed без выдуманных страниц.

«Остановить документ» отменяет только выбранный пакет: статус `failed`, worker token отзывается, время/автор записываются в аудит. Оригинал и строки сохраняются. Запоздалые callbacks и сохранение OCR-строк отвергаются. Завершённый пакет отменить нельзя. Повтор возможен только отдельной кнопкой пользователя, с новым worker token.

Отмена не обещает мгновенного завершения уже выполняющегося внешнего HTTP/Tesseract/LLM-запроса. Новый OCR проверяет отмену между страницами; перед каждым новым вызовом Ollama требуется успешная проверка активности пакета. Если старое выполнение n8n ещё работает, остановите его отдельно через GAB 02 → Executions → нужное выполнение → Stop execution. Снимать весь workflow с публикации ради одной строки не требуется.

## Изменения обработки

- Новая аддитивная миграция `20261119_import_progress.sql` хранит начало/завершение обработки, этап, завершённые страницы, execution ID и аудит отмены.
- POST progress принимает только ограниченный worker token конкретного processing-пакета. Исключение из Basic Auth ограничено этими двумя callback-путями: progress и page-result; GET progress, отмена, редактирование, подтверждение и почта сохраняют обычную авторизацию.
- OCR `0.4.7` сообщает фактическое завершение страниц в фиксированный внутренний CRM endpoint; произвольные callback URL не принимаются.
- В GAB 02 остаются 27 узлов. OCR получает batch/token, claim сохраняет execution ID. Запрос Ollama проходит через защищённый `/ollama/chat` OCR-сервиса, который передаёт исходный запрос без изменения model/messages/schema в тот же `http://ollama_ai:11434/api/chat` и возвращает ответ с техническими полями номера/последней страницы. Это транспорт для прогресса и проверки отмены; распознавание не переносилось в CRM.
- Установка новой CRM, OCR и GAB 02 должна быть согласованной. Почтовые workflow не меняются; автоотправка и автоподтверждение не добавлены.

## Последовательная обработка и повтор

В HTTP-узел Ollama поступает один элемент с массивом страниц. Пагинация `updateAParameterInEachRequest` посылает следующую страницу только после ответа предыдущей, завершение — `_gab_last_page`, предел — 200 страниц. Исходные model/messages/schema не изменены. Поведение проверено по [исходному коду n8n 2.42.7](https://github.com/n8n-io/n8n/blob/n8n%402.42.7/packages/core/src/execution-engine/node-execution-context/utils/request-helpers/pagination.ts). Обычный Batching HTTP-узла не гарантирует такую последовательность.

Миграция `20261119_import_page_cache.sql` добавляет таблицу `gab_crm_import_page_results`. Каждый завершённый JSON records сохраняется сразу, до перехода к следующей странице. Ключ — пакет и страница; SHA-256 точного запроса (включая текст, модель, промпт и схему) исключает повторное использование другого результата. Страницы не создают карточки CRM: после полного документа остаются проверка и ручное подтверждение. Оборванный JSON и ответ с `done_reason=length` не сохраняются как успешные.

После ошибки нажмите «Повторить обработку» в CRM. OCR/извлечение текста запускается снова; совпадающие LLM-запросы читаются из PostgreSQL, модель вызывается для отсутствующих или изменившихся страниц. Новый worker token получает доступ к прежним результатам того же документа, старый token блокируется. Отмена и запись результата синхронизированы блокировкой пакета. Кэш сохраняется при перезапуске контейнеров и входит в зашифрованный backup PostgreSQL; в Git его нет.

OCR дополнительно допускает только один активный запрос модели (Dockerfile запускает один uvicorn worker). Другой документ получает 429 с предложением ручного повтора, вместо очереди на полчаса. Уже работающий внешний запрос после отмены/сетевого таймаута может ещё завершаться. Повтор документа остаётся ручным. В OCR 0.4.7 допускается одна дополнительная попытка отдельной страницы только при явном `done_reason=length`: лимит генерации удваивается, максимум до 12000 токенов. Общий бюджет двух вызовов — 1800 секунд, перед вторым снова проверяется отмена. При других причинах ошибка возвращается сразу.

Старые ответы из выполнения №157 ещё не находились в этой таблице: новая версия не восстанавливает их задним числом. При первом повторе старого пакета потребуется полная обработка, затем успешно сохранённые страницы можно использовать повторно.

## Установка

После завершения/остановки текущих выполнений, на сервере под root:

```bash
cd /opt/gab
git pull --ff-only
bash scripts/deploy-import-progress.sh
```

Это обёртка над проверенным deploy-all с явной пересборкой OCR из `services/gab-ocr`: для новых callbacks требуется `0.4.7`. Сначала выполняются проверки и зашифрованный backup, затем миграции, CRM/OCR и публикация только GAB 02. При ошибке действует существующий механизм rollback. При активной почтовой отправке или import processing установка блокируется. Если используется приватный deploy.json с закреплённой `ocr_version`, обновите её до `0.4.7`.

Дождитесь `SUCCESS: all`, обновите страницу CRM. Отменённый пакет не запускается снова сам. Оценки страниц появятся для новых/явно повторно запущенных обработок новым workflow, а не задним числом для старой попытки.

## Проверки

Тесты проверяют аутентификацию callback и остальных маршрутов, устаревшие tokens, счётчик без дублей/с учётом перестановки страниц, отмену и её аудит, запрет запоздалого сохранения, сохранность оригинала, запрет отмены готового результата, отсутствие выдуманного ETA, передачу исходного Ollama response и отказ вызывать модель для отменённого пакета. Модель, callbacks и SMTP в проверках заменены; реальных писем не отправлялось. Локальная проверка браузера выполнена на искусственных данных.

Проверяются также сохранение кэша после ручного повтора, отзыв старого token, отсутствие повторных вызовов модели для готовых страниц, отказ при занятости модели, запрет кэширования незавершённого JSON. `node tests/test_import_workflow.js` проверяет восемь страниц, выражения пагинации, остановку на последней, соответствие номеров и запрет неполного/дублированного результата. SMTP/Ollama в Python-тестах подменены.

Проверка выпуска: 67 Python-тестов, 66 успешно, один пропущен (локальный Tesseract отсутствует); Python compile, JS/shell syntax и workflow validation прошли. Дополнительно исполнен подлинный цикл пагинации из n8n 2.42.7 с подменённым HTTP: восемь запросов строго последовательно, максимальная параллельность 1; ошибка страницы 7 останавливает дальнейшие запросы, успешный ответ страницы 8 завершает цикл. Production OCR/LLM и рассылки при проверке не вызывались.


## Ошибка JSON на отдельной странице

Старая ошибка `JSONDecodeError` не позволяла отличить обрыв по лимиту от неверного JSON при обычном завершении. OCR 0.4.7 сообщает `done_reason`, `eval_count`, используемый `num_predict` и позицию синтаксической ошибки, без текста ответа и контактов. Эти поля берутся из [ответа Ollama](https://docs.ollama.com/api/chat); `num_predict` — [предел генерации](https://docs.ollama.com/modelfile), а не время обработки.

При подтверждённом обрыве дополнительная попытка использует те же модель, текст, схему и контекст, меняется только предел генерации. Для увеличенного запроса вычисляется отдельный SHA-256; при повторе проверяются оба точных ключа. Ранее сохранённые успешные страницы с исходным лимитом остаются пригодны, неполный ответ не сохраняется как успешный. Гарантировать корректность следующего ответа модели заранее нельзя; никакие скобки или данные в некорректный JSON автоматически не дописываются.

Регрессии проверяют две попытки максимум, отдельный ключ увеличенного запроса, сохранность прежнего кэша, запрет повторять обычный некорректный JSON, общий deadline, отмену перед дополнительным запросом и отсутствие исходного текста в диагностике.
