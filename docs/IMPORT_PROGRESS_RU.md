# Прогресс и остановка импорта

## Интерфейс

При загрузке показываются текущий файл, процент, переданные/общие МиБ и приблизительный остаток передачи по её фактической скорости. 100% передачи означает ожидание ответа о сохранении файла, а не окончание OCR.

После загрузки карточка автоматически обновляется каждые три секунды. Отображаются очередь, OCR/извлечение текста, извлечение инвесторов Ollama, готовность к проверке, ошибка или остановка; число завершённых страниц текущего этапа и время с начала обработки. Оценка остатка появляется только после двух завершённых страниц и относится к текущему этапу, не к целому документу. Для одностраничного документа, очереди и старого обработчика без измерений время может оставаться неизвестным. Excel-ветка без постраничного OCR показывает этап и elapsed без выдуманных страниц.

«Остановить документ» отменяет только выбранный пакет: статус `failed`, worker token отзывается, время/автор записываются в аудит. Оригинал и строки сохраняются. Запоздалые callbacks и сохранение OCR-строк отвергаются. Завершённый пакет отменить нельзя. Повтор возможен только отдельной кнопкой пользователя, с новым worker token.

Отмена не обещает мгновенного завершения уже выполняющегося внешнего HTTP/Tesseract/LLM-запроса. Новый OCR проверяет отмену между страницами; перед каждым новым вызовом Ollama требуется успешная проверка активности пакета. Если старое выполнение n8n ещё работает, остановите его отдельно через GAB 02 → Executions → нужное выполнение → Stop execution. Снимать весь workflow с публикации ради одной строки не требуется.

## Изменения обработки

- Новая аддитивная миграция `20261119_import_progress.sql` хранит начало/завершение обработки, этап, завершённые страницы, execution ID и аудит отмены.
- POST progress принимает только ограниченный worker token конкретного processing-пакета. Исключение из Basic Auth ограничено этими двумя callback-путями: progress и page-result; GET progress, отмена, редактирование, подтверждение и почта сохраняют обычную авторизацию.
- OCR `0.4.8` сообщает фактическое завершение страниц в фиксированный внутренний CRM endpoint; произвольные callback URL не принимаются.
- В GAB 02 остаются 27 узлов. OCR получает batch/token, claim сохраняет execution ID. Запрос Ollama проходит через защищённый `/ollama/chat` OCR-сервиса. Готовые ответы читаются из прежнего кэша; для новой обработки текст подготовленной PDF/Word-страницы разбивается на фрагменты. Модель, системная инструкция и JSON Schema сохраняются, пользовательское сообщение получает текст конкретного фрагмента. Возвращаются номер страницы и признак последней страницы. Распознавание не переносилось в CRM.
- Установка новой CRM, OCR и GAB 02 должна быть согласованной. Почтовые workflow не меняются; автоотправка и автоподтверждение не добавлены.

## Последовательная обработка и повтор

В HTTP-узел Ollama поступает один элемент с массивом страниц. Пагинация `updateAParameterInEachRequest` посылает следующую страницу только после ответа предыдущей, завершение — `_gab_last_page`, предел — 200 страниц. Исходные model/messages/schema не изменены. Поведение проверено по [исходному коду n8n 2.42.7](https://github.com/n8n-io/n8n/blob/n8n%402.42.7/packages/core/src/execution-engine/node-execution-context/utils/request-helpers/pagination.ts). Обычный Batching HTTP-узла не гарантирует такую последовательность.

Миграция `20261119_import_page_cache.sql` добавляет таблицу `gab_crm_import_page_results`. Каждый завершённый JSON records сохраняется сразу, до перехода к следующей странице. Ключ — пакет и страница; SHA-256 точного запроса (включая текст, модель, промпт и схему) исключает повторное использование другого результата. Страницы не создают карточки CRM: после полного документа остаются проверка и ручное подтверждение. Оборванный JSON и ответ с `done_reason=length` не сохраняются как успешные.

После ошибки нажмите «Повторить обработку» в CRM. OCR/извлечение текста запускается снова; совпадающие LLM-запросы читаются из PostgreSQL, модель вызывается для отсутствующих или изменившихся страниц. Новый worker token получает доступ к прежним результатам того же документа, старый token блокируется. Отмена и запись результата синхронизированы блокировкой пакета. Кэш сохраняется при перезапуске контейнеров и входит в зашифрованный backup PostgreSQL; в Git его нет.

OCR дополнительно допускает только один активный запрос модели (Dockerfile запускает один uvicorn worker). Другой документ получает 429 с предложением ручного повтора, вместо очереди на полчаса. Уже работающий внешний запрос после отмены/сетевого таймаута может ещё завершаться. Повтор документа остаётся ручным. Для подготовленных PDF/Word-страниц OCR 0.4.8 использует небольшие фрагменты без увеличения лимита при ошибке. Для старых прямых клиентов без стандартного маркера страницы сохранён прежний совместимый режим с одной ограниченной дополнительной попыткой при `done_reason=length`.

Старые ответы из выполнения №157 ещё не находились в этой таблице: новая версия не восстанавливает их задним числом. При первом повторе старого пакета потребуется полная обработка, затем успешно сохранённые страницы можно использовать повторно.

## Установка

После завершения/остановки текущих выполнений, на сервере под root:

```bash
cd /opt/gab
git pull --ff-only
bash scripts/deploy-import-progress.sh
```

Это обёртка над проверенным deploy-all с явной пересборкой OCR из `services/gab-ocr`: для новых callbacks требуется `0.4.8`. Сначала выполняются проверки и зашифрованный backup, затем миграции, CRM/OCR и публикация только GAB 02. При ошибке действует существующий механизм rollback. При активной почтовой отправке или import processing установка блокируется. Если используется приватный deploy.json с закреплённой `ocr_version`, обновите её до `0.4.8`.

Дождитесь `SUCCESS: all`, обновите страницу CRM. Отменённый пакет не запускается снова сам. Оценки страниц появятся для новых/явно повторно запущенных обработок новым workflow, а не задним числом для старой попытки.

## Проверки

Тесты проверяют аутентификацию callback и остальных маршрутов, устаревшие tokens, счётчик без дублей/с учётом перестановки страниц, отмену и её аудит, запрет запоздалого сохранения, сохранность оригинала, запрет отмены готового результата, отсутствие выдуманного ETA, передачу исходного Ollama response и отказ вызывать модель для отменённого пакета. Модель, callbacks и SMTP в проверках заменены; реальных писем не отправлялось. Локальная проверка браузера выполнена на искусственных данных.

Проверяются также сохранение кэша после ручного повтора, отзыв старого token, отсутствие повторных вызовов модели для готовых страниц, отказ при занятости модели, запрет кэширования незавершённого JSON. `node tests/test_import_workflow.js` проверяет восемь страниц, выражения пагинации, остановку на последней, соответствие номеров и запрет неполного/дублированного результата. SMTP/Ollama в Python-тестах подменены.

Историческая проверка OCR 0.4.7: 67 Python-тестов, 66 успешно, один пропущен (локальный Tesseract отсутствует); Python compile, JS/shell syntax и workflow validation прошли. Дополнительно исполнен подлинный цикл пагинации из n8n 2.42.7 с подменённым HTTP: восемь запросов строго последовательно, максимальная параллельность 1; ошибка страницы 7 останавливает дальнейшие запросы, успешный ответ страницы 8 завершает цикл. Production OCR/LLM и рассылки при проверке не вызывались.


## Ошибка JSON на отдельной странице

В старом прямом режиме ошибка `JSONDecodeError` не позволяла отличить обрыв по лимиту от неверного JSON при обычном завершении. Совместимый режим, добавленный в OCR 0.4.7, сообщает `done_reason`, `eval_count`, используемый `num_predict` и позицию синтаксической ошибки, без текста ответа и контактов. Эти поля берутся из [ответа Ollama](https://docs.ollama.com/api/chat); `num_predict` — [предел генерации](https://docs.ollama.com/modelfile), а не время обработки.

При подтверждённом обрыве дополнительная попытка использует те же модель, текст, схему и контекст, меняется только предел генерации. Для увеличенного запроса вычисляется отдельный SHA-256; при повторе проверяются оба точных ключа. Ранее сохранённые успешные страницы с исходным лимитом остаются пригодны, неполный ответ не сохраняется как успешный. Гарантировать корректность следующего ответа модели заранее нельзя; никакие скобки или данные в некорректный JSON автоматически не дописываются.

Регрессии проверяют две попытки максимум, отдельный ключ увеличенного запроса, сохранность прежнего кэша, запрет повторять обычный некорректный JSON, общий deadline, отмену перед дополнительным запросом и отсутствие исходного текста в диагностике.

## Диагностика повторного таймаута

Если после установки страница снова заканчивается `TimeoutError`, не повторяйте документ вслепую и не увеличивайте таймаут. Сначала выполните под root:

```bash
cd /opt/gab && git pull --ff-only && python3 scripts/audit-import-runtime.py --batch-id 8 --execution-id 469
```

Это отдельная диагностика, не deploy: только SELECT в read-only транзакции, inspect/stats и чтение логов контейнера, GET health/version/ps. Скрипт не вызывает `/api/chat` или `/api/generate`, не меняет модель/контейнеры/статусы, не отправляет письма. Показывает номера и метрики сохранённых страниц, активные импорты, версии, ресурсы, настройки параллельности и длительности последних HTTP-запросов Ollama. Из логов выводятся только отфильтрованные числовые метрики и счётчики признаков ошибок. Тексты документов/ответов модели, worker tokens, пароли, окружение целиком и execution payloads не выводятся. Ошибки команд скрываются, недоступные разделы помечаются `unavailable`.

Отсутствие данных в `/api/ps` после ошибки не доказывает, что модель не была загружена во время сбоя; это снимок текущего состояния. Параметры batch/execution позволяют проверить другой пакет без изменения скрипта.


## Фрагменты для страниц, которые не завершаются целиком (OCR 0.4.8)

Аудит пакета №8 подтвердил шесть сохранённых успешных страниц и повторный таймаут страницы №7. Активных импортов на момент аудита не было. GTX 1060 имеет 6 ГБ VRAM, готовые ответы генерировались примерно с 12–15 токенами/с. Снимок `/api/ps` был пустым: он не доказывает использование или отсутствие GPU во время предыдущего запроса. Причина замедления/ошибки самого Ollama этим снимком не установлена; серверная модель и её глобальная конфигурация не меняются.

Новая обработка подготовленных PDF/Word-страниц сначала проверяет прежние точные ключи полного ответа: готовые страницы 1–6 не удаляются. Для ещё не готового ответа формируется план фрагментов до 1200 символов, с перекрытием не менее 240 символов и предпочтением границ строк. Весь исходный текст покрывается, максимум — 32 фрагмента. Для каждого запроса используются `num_ctx=4096`, `num_predict=2000`, timeout не более 300 секунд. Общий бюджет свежих запросов в одной попытке страницы — 1800 секунд; неоконченный JSON не дописывается автоматически и не сохраняется как успешный. Пустой или слишком большой документ по-прежнему требует проверки, пределы не обходятся.

Аддитивная миграция `20261120_import_fragments.sql` добавляет `progress_detail` и `gab_crm_import_page_fragments`, где ключ состоит из пакета, страницы и SHA-256 точного запроса. Сразу после успешного фрагмента результат фиксируется в PostgreSQL. При ручном повторе каждый готовый фрагмент читается из БД; отмена и смена worker token запрещают старые записи/чтения. После всех фрагментов сохраняется объединённый ответ с отдельным ключом плана. Он выдаётся в прежний 27-узловой workflow без изменения credential references. Excel-ветки и рассылки не меняются.

Результаты соседних фрагментов могут содержать одну запись дважды: кандидаты сохраняются и отмечаются «Возможный повтор на границе фрагментов». Автоматического удаления или объединения компаний/контактов нет. Каждая строка многосоставной страницы помечается для проверки оригинала и содержит номер исходного фрагмента. Ручная проверка, match-preview и подтверждение переноса остаются обязательными.

В интерфейсе отображается «Страница 7: готово фрагментов 2 из 5». Заголовок статуса и кнопки «Повторить»/«Остановить» обновляются вместе с результатом опроса, чтобы «Ожидает обработки» не оставалось над уже завершившейся ошибкой. Для этапа с фрагментами численный ETA по числу страниц отключён: попадания в кэш не считаются измерением скорости будущих запросов.

Установка — той же командой `bash scripts/deploy-import-progress.sh` после `git pull --ff-only`, без автоматического повторного запуска пакета №8. По завершении `SUCCESS: all` повтор запускается пользователем в CRM. Время и качество результата на реальной модели требуют этой проверки; локальные тесты заменяют Ollama искусственными ответами и не доказывают скорость production GPU.

Проверка 0.4.8: 81 Python-тест, 80 успешно, один пропущен из-за отсутствия локального Tesseract. Проверены реальный PostgreSQL, повтор миграции с сохранёнными фрагментами, отдельные области кэша, отзыв токена, восстановление после частичного сбоя и настоящий age backup/restore искусственной БД. Дополнительно прошли `node tests/test_import_progress_ui.js`, `node tests/test_import_workflow.js`, Python compile и shell/JS syntax. Реальная генерация Ollama, production-деплой, рассылки и автоматическое подтверждение не выполнялись.
